## CAP & BASE 理论

### CAP

#### 什么是 CAP？

CAP 理论/定理也叫布鲁尔定理，是三个单词首字母组合：  
- C：Consistency（一致性），所有节点访问同一份最新的数据副本
- A：Availability（可用性），非故障的节点在合理的时间内返回合理的响应（不是错误或者超时的响应）
- P：Partition Tolerance（分区容错性），分布式系统出现网络分区的时候，仍然能够对外提供服务

CAP 定理指出对于一个分布式系统来说，当设计读写操作时，只能同时满足以上三点中的两点。   
> 实际上，应该是这么理解：在发生网络分区的情况下，分区容错性 P 必须是实现的，在此基础上，我们只能满足一致性 C 或者可用性 A。  

分布式系统理论上不可能选择 CA 架构，只能选择 CP 或者 AP 架构。 比如 ZooKeeper、HBase 就是 CP 架构，Cassandra、Eureka 就是 AP 架构，Nacos 不仅支持 CP 架构也支持 AP 架构

#### 什么是网络分区？  

分布式系统中，多个节点之间的网络本来就是连通的，但是因为某些故障（比如部分节点网络出了问题）某些节点之间不连通了，整个网络就分成了几块区域，这就叫做网络分区。   

#### 为什么分布式系统不可能选择 CA 架构？  

若系统出现“分区”，系统中的某个节点在进行写操作，为了保证 C，必须要禁止其他节点的读写操作，这就和 A 发生了冲突。如果为了保证 A，其他节点的读写正常的话，就不能保证 C。  

选择 CP 还是 AP 的关键在于当前的业务场景，没有定论，比如对于需要确保强一致性的场景如银行一般会选择保证 CP 。   

注意：如果网络分区正常的话（系统在绝大部分时候所处的状态），也就说不需要保证 P 的时候，C 和 A 能够同时保证。   

如果系统发生“分区”，我们要考虑选择 CP 还是 AP。如果系统没有发生“分区”的话，我们要思考如何保证 CA 。  


### BASE 理论

#### 什么是 BASE 理论？   

BASE 是以下三个短语的缩写：  
- Basically Available（基本可用）：指分布式系统在出现不可预知故障的时候，允许损失部分可用性。部分可用性如下：  
  - 响应时间上的损失：正常情况下，处理用户请求需要 0.5s 返回结果，但是由于系统出现故障，处理用户请求的时间变为 3 s
  - 系统功能上的损失：正常情况下，用户可以使用系统的全部功能，但是由于系统访问量突然剧增，系统的部分非核心功能无法使用。
- Soft-state（软状态）：指允许系统中的数据存在中间状态（CAP 理论中的数据不一致），并认为该中间状态的存在不会影响系统的整体可用性，即允许系统在不同节点的数据副本之间进行数据同步的过程存在延时
- Eventually Consistent（最终一致性）：保证最终数据能够达到一致，而不需要实时保证系统数据的强一致性    

**BASE 理论本质上是对 CAP 的延伸和补充，更具体地说，是对 CAP 中 AP 方案的一个补充。**

#### 分布式一致性有哪些级别？   

分布式一致性的3种级别：  
1. 强一致性：系统写入什么，读出来就是什么（银行转账等场景）
2. 弱一致性：不一定可以读取到最新写入的值，也不保证多少时间之后读取到的数据是最新的，只是会尽量保证某个时刻达到数据一致的状态
3. 最终一致性：弱一致性的升级版，系统会保证在一定时间内达到数据一致的状态（业界推崇）

#### 实现最终一致性的具体方式是什么？   

- 读时修复：在读取数据时，检测数据的不一致，进行修复
- 写时修复（推荐）：在写入数据，检测数据的不一致时，进行修复
- 异步修复：这个是最常用的方式，通过定时对账检测副本数据的一致性，并修复。   


## Paxos 算法

#### 什么是 Paxos 算法？   

Paxos 算法是第一个被证明完备的分布式系统共识算法。共识算法的作用是让分布式系统中的多个节点之间对某个提案（Proposal）达成一致的看法。   

Paxos 算法主要包含2个部分：  
- Basic Paxos算法：描述的是多节点之间如何就某个值（提案Value）达成共识
- Multi-Paxos思想：描述的是执行多个 Basic Paxos 实例，就一系列值达成共识。Multi-Paxos 说白了就是执行多次 Basic Paxos，核心还是 Basic Paxos

#### Basic Paxos 算法是怎样的？   

Basic Paxos 算法中存在三个重要角色：  
- 提议者（Proposer）：也可以叫做协调者（Coordinator），提议者负责接受客户端的请求并发起提案。提案信息通常包括提案编号（Proposal ID）和提议的值（Value）
- 接受者（Acceptor）：也可以叫做投票员（voter），负责对提议者的提案进行投票，同时需要记住自己的投票历史
- 学习者（Learner）：如果有超过半数接受者就某个提议达成了共识，那么学习者就需要接受这个提议，并就该提议作出运算，然后将运算结果返回  

一个提案被选定需要被半数以上的 Acceptor 接受

#### Multi Paxos 思想

Basic Paxos 算法的仅能就单个值达成共识。为了能够对一系列的值达成共识，我们需要用到 Multi Paxos 思想。   

Multi-Paxos 只是一种思想，这种思想的核心就是通过多个 Basic Paxos 实例就一系列值达成共识。也就是说，Basic Paxos 是 Multi-Paxos 思想的核心，Multi-Paxos 就是多执行几次 Basic Paxos。

假设多位拜占庭将军中没有叛军，信使的信息可靠但有可能被暗杀的情况下，将军们如何达成是否要进攻的一致性决定？

## API 网关

#### 有哪些常用的网关系统？   

- Netflix Zuul
- Spring Cloud Gateway
- OpenResty
- Kong
- APISIX
- Shenyu

其中 Netflix Zuul 和 Spring Cloud Gateway 是以微服务的形式存在的，基于 Filter 链的方式来实现网关的各种功能     
OpenResty、Kong 和 APISIX 则是以 Nginx 为核心进行构建的     

#### Spring Cloud Gateway 的工作流程？   

1. **路由判断**：客户端的请求到达网关后，先经过 Gateway Handler Mapping 处理，这里面会做断言（Perdicate）判断，看下符合哪个路由规则，这个路由映射后端某个服务
2. **请求过滤**：然后请求到达 Gateway Web Handler，这里面有很多过滤器，组成过滤器链（Filter Chain），这些过滤器可以对请求进行拦截和修改，比如添加请求头、参数校验等等，然后将请求转发到实际的后端服务。即前置过滤
3. **服务处理**：后端会对请求进行处理
4. **响应过滤**：后端处理完结果后，返回给 Gateway 的过滤器再次做处理。即后置过滤
5. **响应返回**：返回响应给客户端

#### Spring Cloud Gateway 如何实现动态路由？   

Spring Cloud Gateway 是以微服务的形式存在的，当配置更新时需要重启服务，这样不能满足实际生产过程中的动态刷新、实时变更的业务需求    

实现动态路由方式很多，其中一种推荐的方式是基于 Nacaos 注册中心来做。Spring Cloud Gateway 可以从注册中心获取服务的元数据（例如服务名称、路径等），然后根据这些信息自动生成路由规则。当添加、移除或更新服务实例时，网关会自动感知并相应地调整路由规则，无需手动维护路由配置。    

实际运用中，通过 Nacos Server 和 Spring Cloud Alibaba Nacos Config 即可实现配置的动态变更    

#### Spring Cloud Gateway 的过滤器有哪些？   

按照请求和响应可以分为两种：  
- Pre 前置类型
- Post 后置类型

按照过滤器作用的范围可以划分为两类：  
- GatewayFilter：局部过滤器
- GlobalFilter：全局过滤器，最常用的是负载均衡过滤器

#### Spring Cloud Gateway 中为什么不能用 `@RestController 和 @ExceptionHandler` 来进行全局异常处理？   

Spring Cloud Gateway 是基于 Spring WebFlux 构建的，采用非阻塞的反应式编程模型，而 `@RestController` 和 `@ExceptionHandler` 是 Spring MVC (Servlet 模型)的注解，两者属于不同的技术栈    
- **Servlet 模型**：通过 `DispatcherServlet` 处理请求，异常由 `HandlerExceptionResolver` 解析，支持 `@ControllerAdvice` 全局拦截
- **WebFlux 模型**：通过 `WebHandler` 处理请求，异常由 `WebExceptionHandler` 接口处理，与 `@RestControllerAdvice` 无兼容性


## 分布式ID

#### 什么是分布式ID？   

分布式系统中确保数据唯一性的全局标识符，尤其在分库分表、多节点协作的场景下，避免因单机生成ID导致的重复问题    

#### 分布式ID常见解决方案

数据库主键自增方式：
- 通过给不同的分片分配不同规则的ID：比如分片1的ID是奇数，分片2的ID是偶数
- 数据库号段模式：通过预分配号段缓冲池减少数据库压力
  1. 建立全局ID分配表，记录业务类型、当前最大ID、步长、版本号
  2. 服务启动时从数据库批量获取ID区间（如max_id+1到max_id+1000），加载到内存中是用，耗尽后再请求新号段
  3. 通过乐观锁（版本号）解决并发更新冲突  

算法方式：   
- UUID：Universally Unique Identifier，32个16进制数字（8-4-4-4-12）
  - 优点：生成速度通常较快，简单易用
  - 缺点：存储消耗空间大（32个字符串，128位）、不安全（基于MAC地址生成的算法会造成MAC地址泄漏）、无序（非自增）、没有具体业务含义、需要解决重复ID问题（当机器时间不对的情况下，可能导致会产生重复ID）   
- Snowflake 雪花算法：共64bit的二进制数字
  - 符号位：1 bit，始终为0
  - 时间戳：41 bit，单位是毫秒
  - 集群ID+机器ID：10 bit，前5位表示集群ID，后5位表示机器ID（实际项目中可以根据实际情况调整）
  - 序列号：12 bit，自增值，代表单台机器每毫秒能够产生的最大ID数   

开源框架方式：  
- UidGenerator：百度开源的一款基于雪花算法的唯一ID生成器
- Leaf：美团开源的分布式ID方案，提供了号段模式和雪花算法模式
- Tinyid：滴滴开源的一款基于数据库号段模式的唯一ID生成器
- IdGenerator
